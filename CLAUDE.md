# Tavern Landing: working rules
Landing page for "the Unassuming Tavern", the front door to Poly Runner, Bloodsoup Hell and Lifebrained. Don't edit this file without Ricky's approval. Keep it under ~25 lines of rules.

## Session economy
- Search before reading. Never read a large file whole; read only the relevant range. Don't re-read unchanged files.
- Before a big read or wide change, say which files/sections. For multi-step work, propose a short plan and wait for go-ahead before large edits.
- Prefer small, targeted edits over rewrites.
- Filter command output: show failures and the last ~30 lines, not full logs.
- After two failed attempts at the same fix, stop, summarize what was tried, recommend reverting or starting fresh.
- Replies short: outcome first, no recaps, don't paste back code visible in the file.
- Ambiguous requirements: ask one focused question (only if the choice is costly to redo and unclear).
- When a task is done, say so and suggest continuing here or starting fresh.

## Docs
- Stable project facts live in ARCHITECTURE.md, not in conversation. Read only the section you need.
- HANDOFF.md (repo root; overwrite each time; Goal, Done, In progress, Decisions, Next steps, Gotchas; under 40 lines): update after each completed step or major decision. If the session gets long, off-topic or cluttered, say so in one line, update HANDOFF.md first, then recommend a fresh session.
- BACKLOG.md: either of us logs bugs and ideas as `- [ ] (who, YYYY-MM-DD) text`. Don't act on entries unasked. Delete an entry when it's done.
- HISTORY.md: append-only record of every change since 2026-11-21. In the same commit as each change, add one line: `echo '- YYYY-MM-DD HH:MM | branch or version | what changed' >> HISTORY.md` (America/Chicago time). Never edit or delete earlier lines (correct with a new line). It is long, so don't read it unless Ricky asks.

## Testing
- After a change, run only the quick targeted check: headless Chromium at 390px and 1280px, no console errors, all three doors present. After touching `config.js` or `doorUrl()` in `app.js`, also check the resolved links (domain + subdomain, GitHub Page fallback, blank = locked, non-https ignored). Ask before any broad sweep.

## Project
- Static page, no build step, plain JS, no backend, no service worker. GitHub Pages serves `main` from the repo root at Ricky's custom domain.
- `config.js` is the one place for the domain, the three subdomains and the three GitHub Page addresses. Leave a value `''` until Ricky gives it; never guess or invent an address. The `CNAME` file (domain only, one line) is added only when he provides the domain.
- Button names are fixed: "Poly Runner", "Bloodsoup Hell", "Lifebrained". Look: 32-bit pixel art, bright orange and teal, worn wooden tavern floor.
- `assets/floor.png` is generated by `python3 tools/make_floor.py`; change the script and regenerate, don't hand-edit the PNG. Fonts are self-hosted (OFL licenses sit beside them).

## Shipping
- Interactive work goes on `next`; agents never work on `main`. Publish only when Ricky says so: merge `main` into `next`, bump the version (unless docs-only), then push `next` to `main`. Pages publishes from `main` by itself. `.github/workflows/release.yml` makes the `vN` release (tag, zip) from that push; never push tags yourself. Never give Ricky zips or artifacts unless he asks.
- By default, every push to `main` that isn't docs-only bumps `APP_VERSION` (app.js) to the next whole number, in that same push, unless Ricky says otherwise. The next such push makes it 1 (0.1 -> 1), then 2, 3 and so on.
- Docs-only pushes (only `.md` files, `.gitignore`, `.gitattributes`) never change the version unless Ricky explicitly says so. They go straight to `main` by default, then merge `main` into `next`.

## Rules maintenance
- After each release (or on request), suggest changes in one short list: rules to add (friction seen), trim (redundant/outdated/something you'd do anyway), and wording to tighten.
